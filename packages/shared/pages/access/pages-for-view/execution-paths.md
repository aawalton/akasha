## Execution paths: flat fast path vs. LATERAL

Inside the RPC, the union `p_sorts ∪ p_filters ∪ p_resolve_keys` is classified at function-call time per key against four kinds: **promoted column** (`PROMOTED_COLUMN` in `routing-core.ts` / `PROMOTED_KEYS` in `_resolve_sort_value`), **stored attribute** (a property definition with no rollup/aggregate config — value lives at `p.attributes -> '<key>'`), **rollup**, or **aggregate**. Stored-attribute keys are read directly from `p.attributes`; rollup/aggregate keys still need `_safe_resolve_sort_value` to walk the resolver chain. Two paths:

- **Flat fast path** — every referenced key is promoted or stored, every filter is an AND-shape (no top-level `or`), and the sort list is non-empty. The RPC emits a flat `SELECT … FROM pages p WHERE p.page_type_id = $N AND p.deleted_at IS NULL [<inline filter clauses>] [<inline keyset clause>] ORDER BY <key-aware order parts>, p.id ASC LIMIT N`. No LATERAL, no `_pages_row_matches`, no `_pages_project` plpgsql calls, no per-row jsonb aggregation. Filter operators emit inline SQL keyed by kind: promoted keys reference the column (`p.<col> = $N`, `p.<col> ILIKE $N`, `p.<col> = ANY($N)`); stored keys reference the jsonb element (`(p.attributes -> '<key>') = $N`, etc.) with NULL semantics line-for-line identical to `_pages_row_matches`. The `eq` concrete and `inNoNull` operators on stored keys use `p.attributes @> jsonb_build_object('<key>', value)` so the `pages_active_page_type_slug_attributes_gin_idx (page_type_slug, attributes jsonb_path_ops)` index can drive the scan — the composite shape serves both the per-bucket `page_type_slug = ?` predicate and the containment from one scan; multi-element `in` expands to an OR-chain of containment, one term per element. The `page` jsonb is built inline as `COALESCE(p.attributes, '{}') || jsonb_build_object('id', to_jsonb(p.id), …)` — same shape `_pages_project(p, NULL)` would produce. `sort_values` is `jsonb_build_array(<lhs_per_sort_key>, …)`, computed only on the LIMIT-window rows; for stored keys the lhs is `nullif(p.attributes -> '<key>', 'null'::jsonb)` so SQL-null (missing attribute) and jsonb-null (explicit `null` value) collapse to the same SQL NULL — keyset eq-prefix and ORDER BY null-bucketing then agree across the boundary.
- **LATERAL path** — at least one referenced key is rollup or aggregate, OR a top-level filter is an OR shape. The RPC emits the LATERAL aggregator: per-row `_safe_resolve_sort_value` for rollup/aggregate keys (with a CASE arm per stored key inlining `p.attributes -> '<key>'` and another CASE arm per promoted key inlining the column ref, both bypassing the plpgsql dispatch), `_pages_row_matches(p, $filters, rv.value)` for the predicate (idempotent re-eval — stored-attribute filters are also pushed into the outer WHERE before LATERAL so they prune rows early), `_pages_project(p, NULL)` for the projection, and ORDER BY `(sort_vals -> i)`.

Both paths return the same `(page, sort_values, total_count)` tuple shape and the same row sets for any given input — the partition is a planner optimization, not a behavior change. The fast path keeps the inner SQL cost low enough that the planner avoids JIT compilation entirely (default `jit_above_cost = 100000`); on the LATERAL path the dynamic-SQL cost crosses the threshold and JIT runs once per call. The per-operator stored-attribute SQL fragments live in `STORED_OP_SQL`, in the one shared `pages-for-view-stored-clauses.ts` that both paths read; contract-locking tests at `get-for-view-stored-attribute-{filter,sort}.database.test.ts` cover every operator across both paths.
