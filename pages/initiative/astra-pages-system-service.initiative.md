# Intent

- Every write originating off the workstation goes through the pages system service.
- There is one path into page storage, and no writer reaches the store beneath it.
- Every write is admitted by one rule, decided by the page being written and who is writing it, never by which route the write arrived on or which fields it happens to name.
- Every write the service accepts carries who made it, and a write naming nobody is refused rather than recorded.
- No write the service accepts leaves a row pointing at a page held by somebody else, whatever field carries the reference.

# Notes

Opened 2026-08-27 as a placeholder, on Alan's ruling that off-workstation reads and writes go through a successor to the page query service. The read half of that is closed and is recorded below; only the write half is still open, and its shape is Alan's to settle. Nothing is being built here yet.

**The reads are answered off the filesystem, and there is no read service to build.** A pod's repository arrives through an init container cloning akasha onto the node, so `pages/` stands on the pod's own filesystem from pod start. The init container had been fetching against whatever origin an existing clone carried, and a surviving hostPath cache made `code.git` permanent, which is why the manifests naming `akasha.git` never took. Fixed at `63911a51`. It becomes true for each app at that app's next deploy, and redeploying six user-facing apps is Alan's call. The mechanism is on `astra-pages-system-ablation` and is not restated here. Everything that scoped a read service has come off this page: the read half is not deferred and not blocked, it is not wanted.

**What holds `@shared/pages-query` in place is not a service either.** `askComposed` has 60 callers on `@shared/pages-query/ask`, and a third implementation at `tools/lib/page-query-client.ts:90` answers 12 more in process — three implementations of one function. The in-process repoint landed at `58e35244e` on Alan's ruling: "you can repoint for now, and then we can migrate onto the new clean core once it can support the case." What blocks that migration is that `pages-system/query/`'s `Query` lacks `sort-by`, `descending`, `limit`, `offset`, `count-by`, `function`, `target` and an object `where`. Closing that gap is what retires it, and it belongs to the core rather than here.

**Two workstation services were left pointing at this service's absence.** `services/daily-tracking-points.ts:41` and `services/great-courses-sync.ts:38` each run `process.env.PAGE_QUERY_ORIGIN ??= pageQueryOrigin()`, which `58e35244e` made throw where the variable is unset. Both documents are `enabled: true` and run here, so they were never off-workstation callers and never customers of this service. `daily-tracking-points` took the throw on every hourly run from 20:00 on 2026-08-27 and nothing reported it, filed as `pages/finding/workstation-service/a-workstation-service-failed-every-hour-and-nothing-said-so.finding.md` and repointed in process by another seat.

**The page query service is gone, not down.** Its document was deleted at `620c77034` and `7411bbd8c`, taking `port: 8787` with it. `pageQueryOrigin()` at `tools/lib/page-query-client.ts:40-44` now answers the stated environment variable and refuses plainly otherwise, so a caller through that module fails where it is rather than reaching a dead port. A caller through `@shared/pages-query` still reaches the dead port, that package resolving the cluster origin as a constant.

**The predecessor was never cluster-resident, and this is the most load-bearing fact about it.** It was a workstation service wearing a cluster alias: its document stated `port: 8787` and `namespace: page-query-service`, and `ops service install` composed a namespace, a selector-less ClusterIP and an EndpointSlice addressing this workstation, at `tools/lib/service-cluster-reach.ts:33-79`, the address read from `ip route get 1.1.1.1`. Off-workstation page access has always meant the cluster phoning the workstation over HTTP. That mechanism is generic and already built, so cluster reach is not a thing a write service would have to invent.

**Two of those aliases are still standing, and both advertise that they are ready.** `page-query-service` on 8787 and `graph-service` on 8788, each `managed-by: ops-service-install`, each addressing `192.168.68.50`, where `ss -ltn` shows nothing. Both documents are deleted and `rg '^port:' pages/**/*.md` now answers nothing, so the mechanism has no document left anywhere and both artifacts remain. **This is Answer Or Refuse broken in infrastructure**: what the cluster answers about whether a service is up is a literal written at install time, `conditions: ready: true` at `service-cluster-reach.ts:71-72`, so the one reading that could report the outage is the one that cannot change. A caller gets a refused connection where no endpoint is the true answer. Filed as `pages/finding/service/every-workstation-service-given-a-cluster-alias-leaks-one-on-removal.finding.md`. Whatever is built here must not become the third.

**Four intents above came off four findings that closed without being fixed**, their Postgres substrate having been deleted under them: `cross-owner-relation-writes-unguarded`, `unattributed-write-clears-user-content`, `owner-guard-misses-unset-writes` and `raw-sql-upsert-bypasses-owner-guard`. They are four sightings of one failure — the guard was attached to something other than the store, to a route or a layer or a field in the payload, so anything arriving by another door or omitting that field was admitted unchecked. Two riders do not follow from that unity and so stand on their own: knowing a writer may write does not record that they did, and admitting a write says nothing about whether what it says is sound.

**The referential rule wants measuring before its form is chosen, and that was never done.** Two of the four named the sequence and neither discharged it: enumerate the cross-owner references that actually exist, then decide between universal, universal-with-exemptions, and opt-in. The one measurement anyone took says universal is nearly free — 975 references across four tenant relations, cross-owner rows in exactly one of them, 12 of 22 on `temper-task.character` and every one of those the incident, with 953 references across the other three clean. Counting call sites is not this measurement: 96 of them answer who calls a writer, not who would write across a boundary.

**Held by somebody else does not mean held by another name.** The rule as originally proposed exempted a sentinel holder, which is how a page shared by the system rather than owned by a person was represented. A rule with no such carve-out refuses legitimate writes, so whatever plays that part here has to be named before the rule is built, or it will be rediscovered by breaking something.

**A test naming no path is a false global claim.** The old guard made owner-crossing impossible on one route and left it open on another, and a test asserting impossibility without naming the route it guards asserted something untrue of the system. Every test of these four intents states which path it holds. And a guard is confirmed by watching it refuse, not by a commit message saying where it was wired.

**Nobody ever found what made the unattributed write.** The sweep across other pages and users was never run, on a field where one page alone carried 376 versions, and the forensic handle was left written down: the empty-paragraph payload is the signature to look for. The intent above says a write must carry who made it; it does not say the original question was answered, because it was not.

**One of the four is live today, unchanged in shape.** A writer reaching the store beneath the guarded layer was raw SQL then; it is `tools/lib/page-rows-write.ts` now, outside the layer this service is being built on. Nothing about that one was repaired by the substrate going. `rowAppender` at `:281` appends straight to disk through `appendFileSync` at `:319`, beside the `landRows` and `landAppended` path; the words owner, actor and writer appear nowhere in its 13,735 bytes; and `chess-puzzle/sync.ts`, `chess-puzzle/solve.ts`, `log-append.ts`, `image-row-write.ts` and `page-query-landing.ts` all reach it. So its finding stays filed, rehomed onto that address rather than removed — an intent says there should be one path, which is not the same record as a finding saying there are two and giving the second one's location.

**What went with the substrate, and must not be carried forward.** Per-row ownership: no domain page names an owner or a user id anywhere, so a property phrased as cross-owner has nothing to bind to for a file-backed page. Row-level security as the thing that hid the harm: a wrong relation in a file shows up in a grep and a diff, where in the old world rows rendered blank and nobody saw it for a minute or a month. Opt-in versioning as the recovery story: git gives every file-backed page unconditional history. **Whether a sidecar is recoverable the same way is open, and it is the question that matters** — the file is not the whole page, and rows are where this bites.

**Ownership concentrates in rows rather than disappearing.** Data a product collects at runtime stays a row, and the one measured incident was a product's tenant data, not authored files: twelve of Alan's rows pointed at a throwaway account's pages within a minute, invisibly and unrecoverably. A file-backed answer does not reach that case, and this service is what stands in front of it for products. So the referential intent is worth more here than the other three, not less.
**`pages-system/store/` has no caller at all.** Twelve files outside `pages-system/` import from it and all twelve import `pages-system/page-type/`; `store/`, `query/`, `formula/` and `name/` have no external importer. The only mention of `pages-system/store` elsewhere is a doc comment at `pages-system/query/query.ts:26`. A service over the store would be its first consumer, which means nothing to migrate and no evidence yet that the surface is the right one.

**Two of the store's answers cannot cross a wire, and that is the sharpest constraint on the design.** `rowsIn` returns `Iterable<RowPage | RowUnread>` at `pages-system/store/rows.ts:116` and `rowPagesIn` returns `Iterable<Page | Unread>` at `store/row-pages.ts:112`. Both are deliberately lazy and give a fresh walk on each `[Symbol.iterator]`, because `log-line` holds 3.6M rows and materialising them cost 6,924 MB. A call and its answer cannot express that, so the operation that most needs to stream is the one this service cannot carry in the obvious shape. Whatever is proposed here says what it does about rows before it says anything else.

**The singular readers are the batch readers with a whole tree walk each.** `pagesOf` is written on `pagesFor` and `declarationOf` on `declarationsFor`, so a singular call walks the tree. Across a network that is one traversal per call. The batch pair is the surface; the singular pair is not.

**The old service was a hop, not an implementation.** `services/page-query-service.ts:9-23` imported `tools/lib/page-query.ts`, `page-query-answer.ts` and `page-query-landing.ts` — the same modules a command calls directly. Nothing inherits logic that lived only there.

**The successor holds no store of its own.** The parent's first intent names the service inside the clean set, so it is a skin over `pages-system/` and this initiative has one job rather than two. A store reached only through the service would be a competing implementation, which the parent's second intent forbids.

**The open question is the write path's shape, and it is Alan's.** Does a remote write run the akasha gates against this workstation's live tree and commit here, accepting one contended lock and a single point of failure for every product write, or do product writes go to sidecar rows on a path that is not `ops write` at all? `pages-system/` does no I/O and `store/` reads and does not write, so there is no write seam beneath this to build on; the row writers are still `tools/lib/page-rows-write.ts`. The gates read the live working tree, which every other agent is changing at the same time, and the commit serialises on one exclusive landing lock. This sits behind a question of Alan's already queued, and nothing here is designed past it.

**The general fault, and it is this initiative's own inheritance.** Each repair here moved the failure rather than reporting it. The service went down and nothing said so. `feedFor` turned an unreachable service into a person with no feed. The client was made to refuse honestly, and two workstation services turned that correct refusal into an hourly failure nobody was told about. The deployment was deleted and left cluster objects nothing can now remove. A successor that answers a reachability failure as an empty result, or that goes away leaving something still claiming to be ready, repeats the thing that made the predecessor worth deleting.
