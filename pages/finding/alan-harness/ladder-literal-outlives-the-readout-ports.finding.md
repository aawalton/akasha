# Claim

The green-day-units ladder has one consumer no readout project retires: a faucet folding the same rows to a different reading, which needs the literal standing.

# Evidence

Reported independently by the seats on #18908 and #18909 on 2026-08-12, from opposite sides of the same seam.

`GREEN_DAY_UNITS_LADDER` stands in `daily-stoplights.ts`. #18908 ports the value and inbox readouts to SQL and would delete it; #18909 closes `upkeep-stoplights.ts` and `persona-stoplights.ts` behind it. Those account for every readout consumer.

`stoplight-mean-points.ts` is the one left. It is the `stoplights` faucet, and it folds the same relationship-progress rows to a DIFFERENT reading: the six value circles with one persona held out, settled to a fixpoint. No function answering a readout answers that, so it needs `aggregateValueUnits` and the ladder to keep standing. `faucet-document-check.ts` reads the ladder too.

So #18792's first criterion — that searching the code repository for one of these values finds the reader rather than a literal — cannot fully pass on the readout projects alone. One literal survives them all, with a live consumer that is not a readout.

Neither seat absorbed it and neither was asked to. Widening either project to cover a faucet fixpoint would have been stretching a readout port around something that is not a readout.

What would settle what this means: whether the faucet's fold should read the same projection the readouts now read, or whether a second reading over the same rows is a thing the system means to have. That is a question about the faucet rather than about the ladder.
