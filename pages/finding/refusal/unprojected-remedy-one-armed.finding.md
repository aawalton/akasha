# Claim

The remedy on `refusals/project-status-unprojected.md` is one-armed: it names only the `adding` escape, never the ordinary act of landing the value in the union and deploying. The drift has two honest causes, and on the second — a projection that never received a value the declaration has carried for some time — `adding` mislabels a real gap as a change in flight and quiets the check without the vocabulary ever agreeing. The sibling `project-status-undeclared` names both arms of its case.

# Evidence

Raised by the dispatched `review-instructions` seat reading the document on 2026-08-12, which probed the arm once per rollout mark and confirmed the remedy the document does name clears the check.

Why it did not land the second arm: wording it means deciding how much of the cross-repo sequence a refusal carries. `tools/lib/project-statuses.ts` puts that sequence in `ops project status-options`' help on the ground that an instruction is not a code comment — but that command writes the options row rather than the union this refusal is about, so its help is not simply citable here.

Not measured: which of the two causes actually produces this drift in practice.
