# Claim

`code-comment.md` bars every comment outside the six forms across `**/*.ts`, and its own Intent records that the code repo has not reached that. The rule binds each new comment while the tree around it contradicts it wholesale, so a seat writing code either violates it or stops to ask. The prose comments are also load-bearing: verifying #19053 turned on two of them, and was misdirected by a third that had drifted exactly as the rule predicts. Nothing settles which way this goes.

# Evidence

## Where this came up

Raised by #19053's seat in its hand-back: the rule allows only the six forms, the code repo is saturated with prose comments, and the seat had written more. It asked for a ruling, judging it bigger than its own project. The lead agreed and is filing it rather than ruling in the work.

## What one run produced on both sides

The lead verified #19053 by running its instruments rather than reading its account, and prose comments decided how that went — twice for, once against.

FOR. `packages/agents/shared/spawn-state.ts` carries a docstring predicting the exact failure the project existed to repair: a list falling behind the grammar would under-count live children and read a busy manager as idle. `packages/agents/devops-monitor/src/wedges/seat-derivation-coverage.ts` explains why its denominator is deliberately not a derivation, and why a zero with no denominator must read `unobserved` rather than `clear`. Neither is expressible as a domain line, both being about why one function is shaped as it is. The second was the difference between checking the criterion and understanding it.

AGAINST. `parseProjectSeqFromHandle`'s docstring in `packages/agents/shared/project-binding.ts` still names five consumers as staying on the narrow parse when #19053 moved all five off it. Two paragraphs above, the same comment records that an earlier stale note "sent each later audit to a function that no longer does" — then repeats it. Filed as `pages/finding/agent-harness/stale-name-parse-routing-note.finding.md`.

## Why it costs something standing unsettled

Every seat writing TypeScript in the code repo meets this, and both readings — obey the rule and lose what the good docstrings carry, or write them and stand outside a rule that binds — are defensible from inside the work. That shape produces a different answer per seat, and nothing shows which was taken.

## Delete this when

The rule is narrowed, the Intent withdrawn, or a ruling makes plain what comments the code repo may carry.
