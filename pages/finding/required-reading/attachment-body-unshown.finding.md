# Claim

A file whose name matches `.declaration.attachment.ts` is classified as generated, so `ops read` records it read whole and prints none of its body. No flag recovers it: `--full` returns an ordinary file's body and still returns nothing for one of these.

The read-before-write gate is satisfied by that record. A write to such a file therefore passes a gate whose whole purpose is ensuring the writer saw what they were changing, having been shown none of it.

These files are not generator output by any reading. They are hand-authored TypeScript that CI discovery imports and executes: the shell commands CI runs stand in them as authored string literals, and a path written into one is a path CI will use.

`ops read` already holds the principle that a read record nobody read is a lie. It refuses when its output goes to a pipe, and says why: no body would reach the agent, and a record would have said one had. The generated classification produces that same state for this class of file and does not refuse.

What this hides is absence read as compliance, where the absent thing is the agent's knowledge of the body and the compliance is a green gate.

# Evidence

# Mechanism

`generated-file/generated-file.ts:17` returns true for an attachment that is not a code attachment:

    if (isAttachmentFile(relPath) && !isCodeAttachmentFile(relPath)) return true

`page/attachment-file.ts:12-14` defines `isCodeAttachmentFile` as requiring a `.code.` infix:

    return /\.code\.(?:uncommitted\.)?attachment\.[a-z0-9]+$/.test(relPath)

A `.declaration.attachment.ts` file carries the attachment key `declaration`, fails that test, and is therefore classified generated by line 17.

`tools/lib/workflow-dsl/discovery.ts` sets `DECLARATION_KEY = "declaration"` at line 9, derives the attachment path from its page with `attachmentPathFor(relPath, DECLARATION_KEY, DECLARATION_EXTENSION)` at line 95, and imports the result at line 170. That import is how every CI workflow is discovered, and the steps it yields are run.

# Observed

`ops read` over `pages/workflow-template/workflow-app-namespaces.workflow-template.declaration.attachment.ts` returned only that it was "646 bytes a command wrote whole from something else ... recorded as read whole; nothing follows".

The same call with `--full` returned the same thing, in an invocation where `--full` returned all 26 lines of `pages/task/file-finding.task.md`. The suppression is not a default that a flag lifts.

A repoint across 44 of these files was refused by read-before-write until `ops read` had been run over each. After those reads the gate passed and the write landed. Every one of those records was made without a line of any body reaching the agent that wrote.

Removing one of these files required `cat` to see what it held, `ops read` having declined to show it. `cat` records nothing, so the honest record and the actual knowledge came from two different commands.

# Limits

I did not survey which other attachment keys exist, so I do not know how many kinds of hand-authored attachment fall the same way. I observed it only for `declaration`.

I did not test whether `ops write` or `ops edit` classify generated files as `ops read` does.

I did not establish when this began applying to these files, or whether they were ever shown.

I did not attempt to attribute any particular stale path to this cause. I know that at least one shell command naming a path absent since the repository consolidation stood in this class of file, and that no agent reading those files had been shown a line of them.

No census of affected paths is stated here: that number is changing as the repoint lands, and would rot.
