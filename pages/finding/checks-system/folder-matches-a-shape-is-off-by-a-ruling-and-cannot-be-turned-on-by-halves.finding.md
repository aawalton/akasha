# Claim

`folder-matches-a-shape` is off on all three routes by decision, not by drift. It was born off on 2026-08-27 in `f9f61035d`, "a folder matching none of the defined shapes, as one check under test", and has carried `check-on-patch: false`, `check-on-worktree: false` and `check-on-audit: false` in every one of the seven commits that have touched its page since. Alan's ruling stands at `pages/initiative/thea-checks-system.initiative.md:32` — "This is experimental, leave it disabled."

What is not written anywhere is what undoing that would cost. The check ignores the paths a patch hands it and reads folders off disk rather than off the patched tree, so `check-on-patch: true` refuses every write in the repository on all 1,258 failures at once, rather than on the failures a change touches. There is no partial route: the flag is all-or-nothing as the check stands. The 569 recorded at `pages/initiative/astra-pages-system-folder.initiative.md:21` is stale by more than double.

# Evidence

Read in the tree on 2026-08-27. `checks-system/check/folder-matches-a-shape/folder-matches-a-shape.check.md` carries `check-on-patch: false` at line 8, `check-on-worktree: false` at line 9 and `check-on-audit: false` at line 10.

The three flags were never true. `git log` on that page returns seven commits, and `git show <commit>:<path>` at each returns all three as `false`: `f9f61035d` "a folder matching none of the defined shapes, as one check under test" (12:26), `056c13434` "One name for one thing: folder shape" (12:32), `a6019b1a8` "ryn: shape 1 is a single code entry, and a type declaration file is not a code file" (13:25), `e1ef8a0ab` "ryn: the check does not enumerate the shapes" (13:26), `53db82ce4` "ryn: shape 1 is single-code-entry, and a type declaration is not a code file to it" (13:41), `3b5ce5f6c` "ryn: shape 1 is single entrance, named for the folder entrance it counts" (13:58) and `bd4685c23` "page type: claiming is gone, and every site asking what page type a file is of goes through claimant onto pageTypeOf" (18:01). All seven are 2026-08-27. Nothing was switched off; the check has never run on any route.

The reason is on record, and later than the check. `efcc0f577` on 2026-08-27 at 20:23, "Record on the initiative the rulings Alan made about which checks go on and when", put the line at `pages/initiative/thea-checks-system.initiative.md:32`: "**`folder-matches-a-shape` stays disabled.** \"This is experimental, leave it disabled.\" 1,264 folders fail it on 2026-08-28, the repository root among them."

The count, re-derived rather than taken on report. `ops checks audit folder-matches-a-shape` on 2026-08-27 reports 1,258 failures, the repository root `.` among them. The audit reaches it despite `check-on-audit: false` because a check named on the command line runs anyway, which is what `ops-cli/checks/audit/audit.command.code.attachment.ts:19` states. For a denominator I called `foldersHere()` from `file-structure/folder/folder.ts` directly: 3,356 folders are known, 2,885 hold at least one file and so are judged, and 471 hold none and are skipped by `folder-matches-a-shape.check.code.attachment.ts:135`, which is how the `subfolders-only` shape is honoured. So 1,258 of 2,885 judged folders fail — 43.6 per cent. By first path segment the failures fall heaviest on `temper` (507), `tools` (144), `shared` (130), `infra` (123), `dirty` (118) and `alanwalton` (82).

The 1,264 on the initiative and the 1,258 here are the same reading a tree apart, not a disagreement about the check. The 569 at `pages/initiative/astra-pages-system-folder.initiative.md:21` entered in `933a29d1a` on 2026-08-27 at 18:23, "Split astra-pages-system into three child initiatives"; that line reads the number as a signal for a new package and it is now less than half the true one.

Why the flag is all-or-nothing. `folder-matches-a-shape` declares `needs: tree`, and `checks-system/run/all.ts:22-25` hands a tree check the changed paths and lets it decide what to do with them. `folder-matches-a-shape.check.code.attachment.ts:129` destructures `({ root })` alone — `paths` and `tree` are never read. Line 130 calls `foldersHere()` and line 131 calls `diskFileTree(rootsHere())`, both of which read the working tree on disk rather than the patched tree the gate assembled, and line 133 walks every folder in the repository. Every one of the 1,258 failures would therefore be returned against every patch, whatever it touched. That is exactly the condition Alan's other ruling on the same initiative forbids: "a change set that does not touch a failing file must not be blocked by it". Turning the flag on without first scoping the check to `paths` would stop every write in the repository.

It is the only check off on all three. Of the fifteen `*.check.md` pages, `folder-matches-a-shape` is the one carrying an explicit `false` on all three keys. Six more carry `check-on-patch: false` and `check-on-worktree: false` and say nothing about `check-on-audit`: `import-resolves`, `links-resolve`, `page-holds-to-its-type`, `page-name-unique`, `read-what-is-required` and `require-import-extension`. Those six are not decorative, because absence is not false: `pages/page-property-definition/check-on-patch.page-property-definition.md:8` states `default: true` and `checks-system/checks.ts:84` reads `said !== false && said !== "false"`, so an unstated key runs. Each of the six runs on audit and refuses nothing, so seven checks in all refuse nothing today. `read-before-write` states none of the three and so runs on all three.

The off state is visible in the model, not only in the flags. All three shape pages under `pages/folder-shape/` name `check-slug: folder-matches-a-shape`, and `statusesIn()` from `file-structure/folder-shape/folder-shape.ts` answers `coded` for all three — "a shape a check runs, refusing nothing" — because `refusesChange` reads only `check-on-patch` and `check-on-worktree`. No shape in the repository reads `enforced`.

One thing else turns on the flags staying false. `checks-system/checks.ts:98-102` records that a check standing down in all three phases never has its module loaded at all, so a broken attachment beside it cannot wedge `ops write`, `ops edit` and `ops mv`. That is a property this check currently has and would lose on any route being turned on.
