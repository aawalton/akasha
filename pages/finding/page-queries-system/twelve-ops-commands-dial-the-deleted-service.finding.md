# Claim

Thirteen `ops` commands were run read-only on this workstation and twelve of them refused, each dying on the same dial: `http://page-query-service.page-query-service.svc.cluster.local:8787`, the in-cluster address of a service deleted for good. The ablation that deleted the page query service installed the in-process answerer in the two long-running services and nowhere else, so `ops` itself was never carried over. The dispatcher installs no fetcher, the launcher preloads nothing, and `@shared/pages-query` falls back to native `fetch` when nothing is installed — so every `ops` command whose read runs through that package reaches for a machine that is gone.

This is not a latent path. `ops exercise today`, `ops exercise digest`, `ops exercise next-set`, `ops tower state` and `ops mobile cut-status` are the ordinary way those areas are read, and all of them exit 70 having read nothing. Thirty-nine command modules under `tools/commands/**` reach `@shared/pages-query` through their import graph; of the thirteen safe to run read-only, twelve were confirmed broken and one was confirmed unaffected, and the remaining twenty-six write, deploy or drive a device and were not run.

The commands that still answer answer for a reason, and the reason is that they never touch `@shared/pages-query`. `ops tracking status`, `ops page query`, `ops exercise policy-show` and `ops page types` read the checkouts in process through `tools/lib/page-query.ts` and `tools/lib/tracking/pages.ts`. So the pages system has two read routes on this workstation: one that reads files in process and answers, and one that dials and cannot. Which route a command takes was settled by which library it happened to import, not by any decision about where a read should come from.

# Evidence

Run on 2026-08-28 against `6387c8f4f` on `main`, and re-confirmed against `95bd5ce3f` on `main` after the tree moved under the measurement. Every command below was invoked as `timeout 90 ops <argv>` with its exit code and wall time recorded.

**Twelve read-only commands refuse, all on the same dial.** Each exited 70 in 2.1–3.0 seconds with one line naming the cluster origin: `ops exercise today`, `ops exercise constraint-list`, `ops exercise equipment-list`, `ops exercise digest`, `ops exercise ranks`, `ops exercise mobility-show`, `ops exercise history --exercise "Bench Press"`, `ops exercise session-show`, `ops exercise next-set`, `ops tower state`, `ops tower snapshot`, `ops mobile cut-status`. The line for `ops exercise today` reads: `` `workout-schedule` went unread: `a composed query over `workout-schedule`` went unasked: http://page-query-service.page-query-service.svc.cluster.local:8787/q gave no answer within 5000ms (Error: Unable to connect. Is the computer able to access the url?) ``. Re-run at `95bd5ce3f`, `ops exercise today` and `ops tower state` failed identically.

**The dial is observed, not deduced from the message.** `strace -f -e trace=connect,sendto,socket ops exercise today` shows the process ask systemd-resolved over `/run/systemd/resolve/io.systemd.Resolve`, then four `connect(16, {sa_family=AF_INET, sin_port=htons(8787), sin_addr=inet_addr("10.100.134.88")}, 16) = -1 EINPROGRESS` — one per `ASK_ATTEMPTS` round in `shared/pages-query/src/ask.ts:22-28`. The name still resolves: `getent hosts page-query-service.page-query-service.svc.cluster.local` answers `10.100.134.88`, and `resolvectl query` attributes it to link `tailscale0`. So a caller gets an address and a refused connection rather than a name error.

**Four commands are the positive control and all four answer.** `ops tracking status` exited 0 in 1.1s printing a full day of sessions; `ops page types` exited 0 in 1.5s printing the page type tree; `ops exercise policy-show` and `ops exercise profile-show` exited 0 in ~0.5s; `ops page query --list` and `ops tracking hourly-confirm-pending` likewise exited 0. `ops tracking status` reads through `tools/lib/tracking-capability.ts:143-147` (`pagesAccess`, `pagesClient`) onto `tools/lib/tracking/pages.ts`; `ops page query` reads through `tools/commands/page/query.ts:4-7`, which takes `answerNamed` from `tools/lib/page-query.ts` and the roots from `repo/roots/roots`. Neither reaches `@shared/pages-query`. So the run distinguishes: the commands on the file route pass, and the commands on the HTTP route fail.

**Nothing installs the in-process fetcher for `ops`.** `shared/pages-query/src/fetcher.ts:17-19` is the only installer and `:21-23` returns `chosen ?? (fetch as Fetcher)`. Outside its own package `fetchThrough` has exactly two call sites, `services/daily-tracking-points.ts:3,42` and `services/great-courses-sync.ts:3,39`, both passing `pageQueryInProcess` from `tools/lib/page-query-in-process.ts:82`. `dotfiles/bin/ops:19` is `exec bun "$dispatcher" "$@"` with no preload; `bunfig.toml` preloads only under `[test]`; and `tools/ops/cli.ts` names no fetcher — `grep -rn "fetchThrough\|pageQueryInProcess" tools/ops/ tools/lib/` returns only the definition at `tools/lib/page-query-in-process.ts:82`. Nothing sets `PAGE_QUERY_ORIGIN` in this shell (`env | grep PAGE_QUERY` is empty), so `shared/pages-query/src/index.ts:42-48` falls to the constant at `:8-9`.

**Thirty-nine command modules reach the package, not seventy-two.** A transitive import closure over `tools/commands/**` — resolving relative specifiers and workspace `exports` maps, skipping `node_modules` and `dist` — reports 39 of 297 modules reaching `@shared/pages-query`, at `/var/tmp/pq-graph.mjs`. The twenty-six unrun modules — the `exercise` writers, `food log`, the four `tracking *-sync` commands, `tracking recompute-totals`, `tower commit`, `elaine health-import`, `temper addon-data generate`, the `mobile deploy-*` and `mobile sim` commands, `inference voice-design`, `wan generate` and `wan extend` — write, deploy or drive hardware, and were left alone.
