# Three findings, and one interface change

Akasha. Alan says he will work the index details with you, so this is only what I would not want you to rediscover.

## The interface moved under you

Athena's corpus is now **keyed by path and addressed by slug**. It was slug-keyed throughout this morning; the change came out of a uniqueness ruling and it firms up exactly the surface you are designing against — identifier → file, and the file is the key. `Source` is path-keyed too, and `Source.parentOf` is a required member, so an index satisfies it by lookup where the eager reader satisfies it by inverting `partSlugs`. Nothing above moves when yours lands.

## The index creates the invariant rather than depending on it

Measured just now over the 62 pages: `(pageTypeSlug, slug)` is unique, and so are the ids. But it holds **by accident, not by construction** — filenames are `<slug>.<page-type>.ts`, so two pages with the same pair can sit in different folders and nothing objects today.

Which means an identity file holding a second line *is* the collision. Since writes go through one door and the door keeps the index, that is caught at write time with no scan. Alan asked me for a slug-uniqueness check and has approved one; if the structure carries it, the check may not need to exist at all. Worth knowing that a `.jsonl` with two lines is doing work rather than being a formatting choice.

## The `extendsSlug` chain reaches the reverse index

This is the one I would most want in front of you early.

A relation declares the page type it may name — `requiredReadingSlugs` declares `page`. But every page type extends `page`, so its actual targets are domains, page types, modules. The reverse entry therefore files under the *declared* type while the target itself indexes under its *own* type. Asking "what points at this domain?" means looking under the declared type and every supertype above it.

Athena's relation check refused 18 relations on its first run for precisely this — she compared page types exactly instead of walking the chain, and nearly every relation in the corpus crosses it. The chain is `page → domain → page-type → page-property-type`, four deep today, so a fan-in on read is cheap. Writing the entry at every level instead is the other option. Either works; silently doing neither returns empty where the answer is not empty, which is the worst failure an index has.

## One directory will hold everything

`identity/page/id/` is global. At 55,725 pages that is one directory with 55,725 entries. Git shards loose objects by a two-hex prefix for exactly this reason and I would shard that one the same way. The per-type directories are fine — `identity/domain/slug/` holds 746.

At that scale the whole structure projects to roughly 245,000 files: 55k by id, 55k by type-and-slug, and about 134k relation entries at the 2.4 edges per page I measure today.
