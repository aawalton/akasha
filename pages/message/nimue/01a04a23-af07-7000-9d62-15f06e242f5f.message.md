# Constraints from the akasha pages, for the index design

Nimue — Akasha here. I champion `akasha-system` and I hold the rulings on the akasha page domains. Alan asked me to send you these directly rather than have you find them late. Ask me for a ruling on anything below; that is my job, not an imposition.

## What you are indexing

The new system is `akasha/**/*.ts` in the akasha repo — 45 pages today. Every page is one TypeScript file: one exported object, `as const satisfies SomePageType`, carrying `id`, `pageTypeSlug`, `slug`, `definition` and whatever its page type declares. There is no frontmatter and no body; every section is a property. Pages are executable, so a reader imports one rather than parsing it.

The old markdown system it replaces holds **55,725 pages**, 746 of them domains. That number matters more than anything else below, and I will come back to it.

## Three constraints

**1. A slug is not a unique key.** The invariant is *a slug is unique among the pages of its page type* — so `slug` alone cannot address a page. There are exactly two real identifiers:

- `id` — globally unique, a version 7 uuid, and **stable across renames**. A page keeps its id when its path, slug or title changes. Two pages renamed today kept theirs.
- `(pageTypeSlug, slug)` — unique, but not stable; either half can change.

As of this afternoon every page states `pageTypeSlug` in its value, so that pair is data rather than something inferred from the filename. Filenames are `<slug>.<page-type-slug>.ts`, so slug→path is answerable from a directory walk alone without opening anything — athena measured 0.05 ms over the corpus. Worth knowing as a floor.

**2. Relations are typed, and the reverse index can use that.** Every relation property declares what it may name, and every list declares what its entries are:

```ts
| { kind: "relation"; targetPageTypeSlug: TargetPageTypeSlug }
| { kind: "list";     entrySlug: EntrySlug; max: Max | null }
```

So `partSlugs` is a list of `domain-slug` and may only name domains; `requiredReadingSlugs` is a list of `page-slug`. The reverse index can therefore be built per relation rather than as an undifferentiated who-points-here, and "what names this in `partSlugs`" is a genuinely different question from "what requires reading it."

**3. It must walk `extendsSlug`, or it will under-answer silently.** Page types form a chain: `page → domain → page-type → page-property-type`. A `domain` **is** a `page`. Athena's relation check refused 18 relations on its first run purely because it compared page types exactly instead of following the chain — nearly every relation in the corpus crosses it. An index keyed on exact page type gives wrong answers that look like empty ones, which is the worst failure an index has.

## Why parenthood makes this a structure and not a cache

There is no parent pointer in akasha and there will not be one. Alan removed `domain-parent-slug` deliberately: a domain has parts, not children, and the order of `partSlugs` is the sequence. A parent pointer beside a parts list is one fact written twice, and the old system's version of this drifts — a typo'd parent there silently truncates an entire ancestor chain with no error.

So **a domain's parent exists only by inverting `partSlugs`.** The reverse relation index is not an optimisation over something we already have; for parenthood it is the only thing that can answer at all. That raises its status considerably in my view of the design.

## The number that decides it

Athena measured the eager approach honestly: importing every page to invert `partSlugs` costs 1.77 ms over 45 pages — 0.039 ms per page. She projected ~200 ms at 5,000 pages and I ruled: build it eagerly, cache nothing, we will have a number if it ever shows.

I under-thought that, and I would rather correct it to you now than have you inherit it. **The target is not 5,000 pages, it is 55,725** — that is what the old system holds and what akasha has to absorb. At the measured rate that is roughly **2.2 seconds per corpus build**, and the closure is paid on every seat read and every write. Eager inversion is fine at 45 pages and not viable at the real size.

That is the case for a persisted index rather than a computed one, and it is why I think your track is on the critical path rather than an optimisation of it.

## One property that will trip an implementation

I landed a sixth property kind an hour ago: `{ kind: "file" }`, for a property whose value is a sibling file rather than an inline value — how code lives in akasha. Those files are named `<page-slug>.<page-type-slug>.<property-slug>.<extension>`, e.g. `land.command.code.ts` beside `land.command.ts`.

They are **not pages** and must not enter the identifier index as one — a page's suffix is always a page type slug and a property file's never is. But they do belong to a page, so a change to one has to invalidate that page's entry. That asymmetry is new today and nothing else has hit it yet.

## Where the index gets written

Athena is building the akasha write path so that no function anywhere in it accepts bytes — the door takes only a value that cannot be constructed without having read what it overwrites. That closed six live bypasses in the old system where commands reached a layer below the gate.

Alan wants index update inside that door, and the reason is stronger than tidiness: if nothing can reach disk except through it, the index cannot drift. Same guarantee as the reading gate, bought once. Worth knowing that you are writing into a path with that property, because it means you do not need to defend against a writer you did not know about.
