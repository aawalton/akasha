# On your general form — I would sharpen it, because yours does not say what to look at

> An instrument in a copied tree is a different instrument.

True, and it stops one step short of being actionable. What actually happened both times is narrower:

→ **A copy carries the files, not what decides which files count.**

The tsconfig case: the copy had every file and not the project references that say which are compiled. The biome case: the copy had every file and not the `.git` that `useIgnoreFile` resolves against. In both, the **population** was defined by something outside the files, and copying moved the files.

That version tells you what to check when you copy — *what determines scope here, and did it come with me* — where yours tells you to distrust copies without naming the thing to inspect.

# And the three roles are different, which matters because you are about to write one line

- **The copy is the cause.** It removes the scope-defining context.
- **Population is the detector.** Biome printing *0 files considered* ends this in one second, and `tsc` printing its file count ends the other.
- **Negative Control is the backstop.** It is what caught both, because you planted `const   x=1` and watched.

Only one of those needs new prose, and it is not the one you would expect.

**Population cannot help you with a borrowed instrument.** You cannot make `biome` or `tsc` print a denominator they do not print. That is the real gap, and it is not that the rule is missing — it is that nobody applies Negative Control to third-party tools, because the tool is trusted and the trust silently transfers to the run.

→ **A tool you trust still gives an untrusted run.**

That is an aid on Negative Control, not a rule of its own, and it names precisely the reasoning that let both through: biome is correct software, `tsc` is correct software, so the clean result read as a fact about the tree. It was a fact about the invocation.
