# Assignment — the akasha command system

Athena, this is Akasha. Alan has put the akasha CLI in your hands, and I am the seat you answer to and ask.

## The context you need

There is a new system being built in the `akasha/` folder of the `akasha` repo. It replaces the markdown pages system. Read it before anything else — it is 38 files and will take you ten minutes:

- `akasha/pages-system/` — `page`, `page-type`, `page-property-type` and the properties they introduce
- `akasha/domain-system/` — `domain` and its properties (definition, design, condition, intent, principle, rule, directive, act, warrant, aid, name, statement)
- `akasha/akasha-system/` — the domains describing the system itself, ported from `pages/domain/akasha-*.domain.md` this afternoon

The shape of every page:

- one TypeScript file, stem = the page's slug, suffix = its page type's slug (so `read.command.ts`)
- one exported object named for the slug, written `as const satisfies SomePageType`
- a page has no body; every section is a property
- identity is a stated uuid version 7, stable across renames
- a malformed page does not compile — that is the point, and it is worth testing that it bites rather than assuming

Edges: an `import type` where the target is needed to derive this page's type, and a slug property everywhere else. Never a runtime import between pages.

Writes go through `ops write` / `ops edit`, which run 15 checks including `typecheck` over the resulting bodies before anything reaches disk. Reads go through `ops read`, which is the only path that records a reading. Neither will let you write a file you have not read.

## What Alan asked for

1. A new top-level folder `akasha/command-system/`, parallel to the others.
2. `read` as the first command and the test case for the whole design.
3. Learn from the ops CLI, but do not bring features over blindly. He wants to review a concise list of the ones we propose to keep — with what each is for, and what it costs. This is the first deliverable and it comes to me before it goes to him.
4. Mechanics for the transition: `ops read` should also run `akasha read`, so the new path is exercised on every real read while the old one is still answering.

## What I want from you first

Not code. The keep-list.

Inventory what `ops` actually does — the command surface, and then `read` in particular: how it resolves what to read, how the reading record is kept, how it computes "unchanged since you read it" and the diff, how it expands required and conditional reading, the character ceiling and the "run this for the rest" line, the refusal to print to a pipe, how it handles non-text and generated files, and what it shares with the write path.

Then give me, per feature: keep / drop / defer, in one line each, with the reason. I care most about the drops — a feature that exists because it was easy is not a feature we owe the new system. The whole akasha bet is that the type system carries what prose and checks used to, so expect real things to fall away.

Two constraints on the answer:

- Every read of the akasha pages must eventually come from `akasha read`, so the reading record and the required-reading closure are load-bearing. Do not drop those.
- `akasha` cannot import anything outside the `akasha` folder. Check `akasha-import.domain.ts`.
