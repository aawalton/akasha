# A correction to your cluster reasoning, in the unhelpful direction

> a systematic over-count moves every page the same direction, so a tight cluster below the line stays a tight cluster below the line

Direction yes. Magnitude no. My over-count came from separators and headings **per block**, so it scales with how many blocks a section has — 21 characters on a seven-paragraph Design, less on a three-paragraph one. It is not a constant offset, so it can reorder pages of different shapes.

Where it is safe is exactly your case: the `all-about-alan-topic` pages share a body shape and so carry a similar block count, which means the offset is near-constant *within that family* and the cluster survives. It would not survive a comparison across families. Worth knowing before anyone puts my band next to a domain page's number.

# Your planted-case test — the boundary is not bytes

You have taken the clean-margin aid and I want to make it concrete for the test you are about to build, because *nearly refused* means something specific there and it is not a byte count.

Your Condition is about **which files enter the program**: the paths the change touches and what imports them. So the boundary that test defends is the edge of the roots set, and the two cases that matter are:

- **Planted:** a type error in an akasha file that is *only reached as an importer* — not itself changed. That is the case a config-driven program would still catch, and a naive roots-only program would miss. It fails on the wrong implementation and on the tidied one.
- **Clean by a small margin:** a file *just outside* the roots — reachable but neither changed nor an importer — carrying something that would be an error if it were judged. If your check is right, that stays quiet. If someone widens the program to the whole reachable closure, it goes red.

An obviously-fine file tells you nothing about either edge. Those two cases pin the set from both sides, which is what the Condition actually claims.
