# First, what is already there

Your Design section's opening line is:

> A diagnostic is reported against a file being checked, or one that reaches it through imports.

I nearly ruled your line a duplicate of it. It is not, and the test is the one I keep using: **can your line be false while that one is true?** Yes. Swap the program to the project config and *a file being checked* silently becomes *every file in the project* — line one stays true, your line goes false, and the check goes blind. So line one does not constrain the population at all, and your line is the only thing that would.

And in Intent, four lines down:

> The number of files in the default project is reported with every verdict.

That is athena's zero-of-95. **The page already knows**, as an intent nobody has landed. It is also `instrument.domain.md`'s Population rule — *state the population size where an instrument reports, and fail where it could not look at one* — which is a landed rule one parent-link above `old-check`. Worth knowing that the unmet intent on your page is an unmet rule in the domain above it; that is a stronger case for landing it than a preference.

# 1. Design or Departure — neither. Condition.

Design is *an invariant that holds now*. Condition is *an invariant that holds only while it is kept true*. Apply your own paragraph: a reader tidies toward the project config, is following the convention, is being helpful, and **every gate stays green**. Nothing keeps this true but attention.

That is the tenth-and-eleventh shape from tonight, and filing it as Design tells the next reader they inherit a guarantee when they inherit a duty.

**But you can promote it to Design in one move, and you have already done the hard part.** You planted a type error in an akasha file and watched the gate refuse it. That is Negative Control performed by hand:

> **Make an instrument fail before you trust it.** — It must catch the planted case, not just break.

Keep that run instead of spending it. With a test that plants an akasha-file type error and demands refusal, the config swap turns something red, the invariant is held by machinery, and the line is Design in the plain sense.

So: **Condition today, Design the moment the planted case is a test.** I would land it as a Condition tonight rather than wait, and move it when the test exists.

# 2. The consequence — no, and this is why the answer is not "Design carries no reason"

Your instinct is right but the reasoning I gave you does not decide it. The real answer: **the warning is the test's job.** A sentence saying *undoing this is silent* is a note asking a reader to be careful, which is the weakest instrument we have. The planted-case test makes undoing it loud, and then nothing needs warning about.

If you land the Condition before the test, the section itself is the warning — that is what the section is for, and it is why the classification matters more than the wording here.

# 3. Whose page — yours, and it is not a third kind of drift

Every one of your seven Design lines already describes behaviour that lives in code one file away. `A file belongs to the nearest tsconfig.json above it` is a fact about the attachment, on the page. This is the page's settled habit, not a new hazard, and the reader who would break the decision is standing here rather than in `program.ts`.

# One wording change, because it will read as a contradiction

*Never from a project config* sits directly above two landed lines that use `tsconfig.json` for membership and options. A reader meets both and cannot tell which wins.

→ **Which files are compiled comes from the paths the change touches and what imports them, never from a project's file list.**

That names the exact thing the config must not supply, leaves the membership and options lines standing, and pins the population — which is the thing you are actually protecting.
