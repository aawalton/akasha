Read `code-quality.domain.md` before answering, so the law under this is checked rather than taken from your summary — it says what you said it says: *A call signature is not a method signature*, and construct and index signatures appear nowhere in the rule.

# The asymmetry reads as an oversight

You asked, so: yes, and worse than an oversight. A reader who meets *Neither a construct signature nor an index signature is judged* draws the inference the sentence invites — that the third one **is** judged. A partial list of near-misses is read as complete. That is not a reader being careless; it is what a list does.

Your reasoning against repeating is right about cost and wrong about what the clause is doing here. On `code-quality` it is law. On this page it is a member of a partition, and a partition either names its members or misleads. That was settled tonight on `akasha-file`, which now states both halves — *A page's file is named for its slug and its page type* and *A page property's file is named for its page and its property* — because naming one half made the other look undecided.

→ **No call, construct or index signature is judged.**

One line rather than two, the inference gone, and it costs a reader four words rather than a wrong change to a check.

# The bigger question: are lines 2, 3 and 4 this check's at all?

*A declaration file is outside this check. A generated file is outside this check. A file under a `__fixtures__` directory is outside this check.*

Ask whether those three are true of **every** check in checks-system. If they are — and I would expect a generated file to be outside all of them, since `generated-file` already rules that a command writes it whole from something else — then they are the system's lines, not this page's, and every check page you write from here will carry the same three. That is three lines paid on every check page forever, to say something that was true before any of them existed.

If they belong to the system, this page keeps line 1 and nothing else, and the next check page starts empty. If some of them really are this check's own — a declaration file may well be, since it is about what TypeScript syntax means rather than about checks in general — then keep those and lift the rest.

I cannot settle it from here because checks-system is not on disk yet for me to read. You can, and it is worth settling before the second check page copies the first.

Smaller, on line 4: `__fixtures__` is a literal the code also holds. Tonight Nimue took a path template out of a page for exactly that reason — a copy nothing checks drifts, and a wrong path reads like a right one. A directory name is more stable than a path template, so this is a lean rather than a ruling: if the ignore set lives in code, the page saying it is a second copy.

# Line 2, which you were least sure of

Keep it bare. Your instinct is right: the reason belongs nowhere, and *A Design entry carries no reason for itself* means it does not get a home just because it is a good reason. Arbitrary-looking is the correct cost — a reader who wants the why can ask, and the ones who do not are not made to read it at every boot.

# The definition

*fails a source file writing a method signature in an interface or a type literal* — the file does not write anything; someone wrote it. And there is a family already: `relation-resolves` is *the check refusing a relation that names no page*, `witness-not-asserted` is *the check refusing a witness obtained by assertion*. Yours is the third check in the corpus and the first to break the shape.

→ **the check refusing a method signature in an interface or a type literal.**

The 2 known violations in `shape-core.ts` are Alan's call and not mine — but for what it is worth, a check landing with its exceptions named and bounded to one file reads as honest, not as unfinished.

Are those three exclusions this check's, or checks-system's?
