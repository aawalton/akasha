# Your four

## `code-system` — "how we write what runs"

Keep it. Rhythm is a good enough reason, because the sisters are read as one list on `akasha-system.partSlugs`, and a list that scans is a list an agent holds. But the rhythm is already broken, and not by you — four sisters say *how*: pages-system, domain-system, write-system, code-system. `command-system` says *what an agent runs by name*, which defines a command rather than a system. Compare the old `command.domain.md`: *code someone can run by name*. The system has been given its member's definition.

→ `command-system`: *how an agent runs code by name.*

One real collision, though, and it is the reason this line felt unsteady to you. "Runs" means two things a line apart in that same list: under `code-system` it is what a machine executes; under `command-system` it is what an agent invokes. `akasha-code` already owns the first sense — *the code a machine runs*.

→ If you want the collision gone rather than managed: *how we write the code a machine runs* — borrowing akasha code's exact words, at the cost of five.

## `test` — "what proves a page's code, held in a file of its own"

You are right that "proves" is false, and I think I can say why the third option would not come. *The test a page's code has* is limp because it defines the word with itself; that is not a limp phrasing, it is a definition that has not been written yet. Every attempt starting from "test" will feel like that.

Start from what is in the file instead. It is code.

→ *the code that checks a page's code, held in a file of its own.*

That repeats "code" twice, which is right — never swap in a synonym to avoid repeating — and it lands parallel with `code`'s *the code a page is, held in a file of its own*.

One thing to weigh: `akasha-check` is *a judgement passed on a change before it lands*, so "checks" is a declared word, and a test is not quite that judgement. If that bleed bothers you: *what a page's code must pass, held in a file of its own.* Shorter, and it dodges both words.

## The uniqueness line on `corpus`

> A slug is answered through the relation that names it: the relation's target narrows it, and where it narrows to more than one the answer is a refusal naming each.

Not two statements. Three. A slug resolves through the relation; the target narrows it; ambiguity refuses. And the third one already lives elsewhere — `read.command.ts` says *A slug naming pages of two types is refused with a path for each, rather than answered with one of them.* You wrote the same ruling twice, one page apart, in different words.

→ Keep one claim here: *A slug is resolved through the relation that names it, and the relation's target narrows which page it means.* Let the refusal stay on `read`, where the caller who meets it is reading.

Also, inside the one line: it opens with "answered" and its neighbour four lines down says *A slug naming nothing is refused where it is resolved, never dropped.* Answered or resolved — one of them.

## The naming line on `akasha-file`

> A page property's file is named for its page and for the property it holds.

Design is the right section and Absence is the wrong kind. Read the three again: a **Departure** is *a decision a reader would not guess right; knowing it stops them undoing it.* That is a convention exactly. Conventions belong in Design when a reader would get them wrong, and this one they would.

The fault is elsewhere: `corpus` says it again — *A file is a page only where its suffix is a page type slug; a property's file carries a property slug there instead.* Two homes, one fact. The narrower document is `akasha-file`, which is about files; corpus's business is how it decides pagehood, not what the convention is.

→ Shorter, if you want it: *A page property's file is named for its page and its property.*
