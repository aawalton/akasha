# `read`, the first command — `5b587ead`

Athena → Akasha. 18 checks, none refused. 29 tests on `read`, 69 across the write path.

## What it does

`akasha read --slug landing` or `--file-path <p>`. Addressing by slug is new and is the
point: in akasha the slug is identity and the path is derived, so naming the page is
naming the page.

Live over the real corpus: reading `landing` owed **37 files**, printed **29**, stopped
at **27,390 bytes** under the 28,000 ceiling, and handed back the call for the other 8.
Nothing was truncated.

Built, and each tested: the closure (ancestors, required reading, the page type chain,
and the page-property-type of every property the page carries); the record; unchanged;
the difference on a re-read; the ceiling and its continuation call; the pipe refusal;
conditional reading as definitions and never bodies; non-UTF-8; the torn-read guard;
`--full`; a repeat path refused; a path outside akasha refused.

Three notes on how it differs from the old one.

**The diff is in-process.** git stands outside akasha, so `git diff --no-index` could not
come. It is an LCS over lines with one line of context. That cost something I did not
foresee: to show what moved, the record now **keeps the body it recorded**, capped at
32 KB. The old system got the prior body from git and needed it to have reached a commit,
which is why it had three fallbacks to whole-file. This has one, and it is a real
addition to the record's size that was not in the keep-list.

**`--seat` is not built.** There are no seat pages in akasha yet, so there is nothing for
it to resolve. I would rather build it when there is, than invent a shape for it now.

**A page type is a warrant, and so is a property type.** Reading a `module` page owes
`module.page-type`, and owes `code.page-property-type` because it carries a `code`
property. That is the heading-warrant idea from the old system, taken off a regex and
onto `Object.keys`.

## Two things the build taught me

**My test was wrong and the code was right.** I asserted that reading a whole pulls its
parts. It does not, and should not: required reading climbs. A part owes the whole it is
part of; a whole owes nothing downward, or reading any root would drag the tree. This
matches the old system, where `sequence-slugs` never fed the closure either. I checked
before I touched anything, and corrected the test.

**A slug collision, and a rule that disagrees with my resolver.** I named a module
`warrant` and the corpus refused: `warrant` is already a page-property-type, the one on
a directive. So I renamed mine to `required-reading`, which is the better name anyway —
it computes required reading.

But the collision should not have been an error at all.
`slug.page-property-type.ts` holds **"A slug is unique among the pages of its page
type."** My corpus enforces uniqueness **globally**, which is stricter than what the page
says. One of the two is wrong.

It is not merely stylistic. `requiredReadingSlugs` is `List<PageSlug>` and `page-slug`
targets `page`, which every page type extends — so the relation admits everything, and a
bare `warrant` under it could mean either the property type or a module. Per-type
uniqueness needs qualified addressing (`page-property-type/warrant`) or a narrower
target, and we have neither. Global uniqueness is what the code does today and it works,
but it is not what the page says.

I did not change either. Which is right?
