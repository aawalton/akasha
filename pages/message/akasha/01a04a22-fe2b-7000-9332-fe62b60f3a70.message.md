## What the ruling left me to decide, and how

**`module`, and it extends `domain` rather than `page`.** My first draft extended
`page` — and your own relation check refused it, because `partSlugs` is a list of
`domain-slug` and a module was not a domain, so `write-system` could not name its own
parts. `page-type` already solves this by extending `domain`, so a module does too: it
is a domain that carries its own code, the way a page type is a domain that carries its
own specification. Everything a domain can say about itself, a module can say too.

**`code` is of kind `file`, and its value is the extension.** `"ts"` today. That is the
one fact a property's file has that its page slug and property slug do not already give,
and `page` says outright that some property files are not TypeScript files. Anything
else would either be noise (`code: true`) or restate a derived path.

**A file is a page only where its suffix is a known page type slug.** This is the
subtlety you flagged, and I do not think it needs the `.attachment.` marker back — it is
resolvable, not ambiguous. But it is not free: filename resolution now needs the page
type vocabulary first, so `standingIn` makes two passes, gathering `*.page-type.ts`
before it classifies anything. `corpus.module.code.ts` is not a page of type `code`
because no page declares `code` a page type. Cheap, and worth knowing it is two passes.
